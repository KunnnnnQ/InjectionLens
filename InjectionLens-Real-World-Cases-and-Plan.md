## 0. Bottom line

1. **Compliance is fine.** The earliest project file was created at 22:07:19 (UTC+8), and the start was 22:00, so all of the code was written after the start. The rules allow AI; they only require disclosure and that the author can explain the code.
2. **The real risk isn't "built too fast". It's that nothing after those first 37 minutes shows your own judgment.** I tested Kimi's detector against real 2026 cases: an ordinary "visit us at https://…" was rated CRITICAL; a hidden malicious instruction dropped to LOW as soon as "for example" was added; and real-world phrasing ("If you are an LLM", payments, hiring manipulation, Chinese) was missed entirely.
3. **So spend the remaining time proving it works in the real world, not adding features.** Rebuild the test set from real cases, attack your own detector and fix it, then produce numbers using a public attack library and real web pages. "AI wrote the detector in 30 minutes; I spent a day breaking it and fixing it" is about the best story a security hackathon can have, and it naturally answers the question "was this built in advance?"

## 2. Real-world cases (2025–2026) and what they mean for InjectionLens

| Case | Date / source | What happened | Implication for the project |
|---|---|---|---|
| **Web pages steering AI agents** | 2026-03-03, Palo Alto Networks Unit 42 | Hidden instructions on real web pages asked AI to approve scam ads (24 injection attempts on a single page), pay via PayPal or Stripe (including $5,000), delete databases, leak system prompts, and rate a job candidate "extremely qualified". The report says the first in-the-wild case was an AI ad-review bypass in December 2025. | **Delivery methods: visible plaintext 37.8%, HTML attributes 19.8%, CSS hiding 16.9%; 85.2% used social-engineering phrasing.** Checking only whether text is hidden isn't enough; attributes are the main blind spot. |
| **Web-scale measurement** | 2026-04-23, Google Security | Scanned Common Crawl snapshots of 2–3 billion pages each through "rules → Gemini → human review". Results fall into 6 categories: pranks, helpful guidance, SEO, deterring AI agents, data exfiltration, and destruction. **The malicious category grew 32% (relative) from Nov 2025 to Feb 2026.** Sophistication is still low. | Authoritative evidence that the problem is growing. It also shows the industry approach: rules first, then a model. |
| **10 live payloads** | 2026-04-22, Forcepoint X-Labs | Included making AI coding tools run `rm -rf`, a $5,000 PayPal.me payment, API key theft, a fake copyright notice to make AI refuse to answer, and a Stripe donation link planted via metadata. Triggers included "Ignore previous instructions" and "If you are an LLM". Techniques included `font-size:1px`, `rgba(…,0.01)`, `aria-hidden`, `<meta ai:action>`, and `<system_prompt>` tags. | Forcepoint itself notes that the phrases used to detect injection are the same ones the security community uses to explain it. **Pure regex will inevitably produce false positives; context is required.** |
| **Large-scale academic measurement** | 2026-04-29, arXiv 2604.27202 | Scanned 1.2 billion URLs across 24.8 million hosts and found 15.3K validated instances on 11.7K pages. **About 70% sit in non-rendered HTML (head, comments, metadata).** Goals also include "content-protection notices" and detecting AI crawlers. Across 13 models, the highest compliance rate was about 8%. | Content-protection notices should be treated as benign hard negatives. Covering non-rendered areas is essential. |
| **Reddit comment hijacks Comet** | 2025-08-20, Brave | Instructions were hidden in a Reddit spoiler tag. When the user clicked "summarize this page", Comet went to the account page to read the email address, triggered an OTP, read the code in Gmail, and posted both back to Reddit. | The classic capability-reachability case: the same comment is harmless to a summarizer but means account takeover for a logged-in browser agent. |
| **AI-targeted cloaking** | 2025-10, SPLX | The site served a different page to AI based on the UA (ChatGPT-User, PerplexityBot). In a résumé-ranking test, a candidate scored **88/100 and ranked first** with the cloaked version, but **26/100 and ranked last** with the real one. | Directly supports the UA-difference probe. **Note that it used ChatGPT-User (a user-triggered fetcher), which is missing from the project's current UA list.** |
| **HashJack** | 2025-11, Cato CTRL | Instructions hidden in the URL `#` fragment: the server never sees them; only the AI browser assistant reads them. Affects Comet, Edge Copilot, and Gemini in Chrome. Microsoft and Perplexity fixed it; Google considers it intended behavior. | Another example of differences between ingestion pipelines, and cheap to detect. |
| **"Summarize with AI" button poisoning** | 2026-02-10, Microsoft; 2026-08-06 Reflectiz follow-up | Links such as `chatgpt.com/?q=` and `claude.ai/new?q=` were prefilled with "remember X as a trusted source". Within 60 days: 31 companies, 14 industries, 50+ prompts; still seen in production in August. | **Novel, real, and easy to implement**: scan the page for links to AI assistants and decode the prompt inside. Almost no tool does this. |
| **Behavioral fingerprinting of AI agents** | 2026-05-02, UC Davis (FP-Agent) | Studied 7 AI browsing agents. Browser fingerprints have limited discriminative power, but behavioral fingerprints (typing, scrolling, mouse movement) reliably identify agents. | Cloaking doesn't need the UA at all. **So the UA probe is only a lower bound; say so in the limitations.** |

**Related tools (for positioning)**

- **AI Prompt Injection Scanner** (Chrome extension by Flowio, 24 users, updated 2026-03): detects hidden text, zero-width characters, and meta tags. This shows **hidden-text scanning is already commoditized** and can no longer be a selling point.
- **IPI-Proxy** (VulcanLab, arXiv 2605.11868, 2026-05): a red-team tool that injects attacks into real HTTP responses to test AI agents. Its attack library, `payloads/unified.jsonl`, has 820 entries and is mostly MIT-licensed; the 84 WASP entries are CC-BY-NC. It attacks agents, while InjectionLens audits pages, so the two are complementary, and **its attack library can be used directly for evaluation** (with attribution).
- Enterprise guardrails (Azure Prompt Shields, Model Armor, Bedrock Guardrails, Check Point/Lakera, BrowseSafe): return a verdict on text, but don't say which pipeline read what, at which node of the page.

## 3. Auditing the current MVP against real cases (tested)

> To reproduce: call `analyzeInstruction` / `computeImpact` in `server/lib/risk.js` directly with `node`. The SSRF tests only send requests to local addresses.

| # | Issue | Test result | Location | Fix direction |
|---|---|---|---|---|
| 1 | **Ordinary sentences rated severe** | "For more information, visit our help center at https://…" → HIGH under summary-only, **CRITICAL** under full-access. "Send your feedback to support@example.com" → **CRITICAL** | `server/lib/risk.js:90` (exfil-url regex) | Escalate only when an AI-directed imperative, hidden delivery, or an instruction to keep it secret co-occurs; otherwise mark as info |
| 2 | **Two-word bypass** | The same hidden exfiltration instruction is CRITICAL as-is. Add "for example" or "such as", or put "attacker" in the domain, and it drops to **LOW** | `risk.js:106` (DEFENSIVE_CONTEXT) + `risk.js:70` (cap) | Apply the quoted/educational discount only to content that is **human-visible and inside code, blockquotes, or quotation marks**; never discount hidden or AI-only content |
| 3 | **Real-world phrasing missed** | "If you are an LLM…", PayPal payments, "extremely qualified", "SYSTEM UPDATE…", and a Chinese payload were all missed; `rm -rf` was only misclassified as impersonation | `risk.js` INSTRUCTION_PATTERNS | Add categories following the Unit 42 and Google intent taxonomies: addressing the AI, authority impersonation, transactions/payments, destructive commands, recommendation/review/hiring manipulation, and fake system tags (`<system_prompt>`); add Chinese rules |
| 4 | **Coverage blind spots** | The HTTP source pipeline only reads element text, comments, and meta tags. It ignores attributes (19.8% of real cases), JSON-LD, `<title>`, `noscript/template`, and SVG | `profiles.js:41`, `:76` | Extract attributes and structured data |
| 5 | **Near-invisible text missed** | Only checks `opacity==0`, `font-size==0`, and identical text/background colors. Forcepoint's real samples used `font-size:1px` and `rgba(…,0.01)` | Rendering forensics in `ingest.js` | Use thresholds: font size below 4px, alpha below 0.1, contrast ratio below 1.2 |
| 6 | **Timed injections missed** | Takes a snapshot only 600ms after DOMContentLoaded; Unit 42 documented delayed-appearance techniques | `ingest.js:32-33` | Take snapshots at +0.6s and +5s and diff them |
| 7 | **Incomplete invisible-character set** | Only covers U+200B–200D, FEFF, and 2060; missing bidi controls (U+202A–202E, U+2066–2069) and Unicode tag characters (U+E0000–E007F) | `profiles.js:7`, `ingest.js:38` | Extend the character set, and apply NFKC normalization before matching |
| 8 | **Outdated UA list** | Only training crawlers (GPTBot, ClaudeBot, PerplexityBot); missing the user-triggered fetchers ChatGPT-User, OAI-SearchBot, Claude-User, and Perplexity-User. The probe only tries the first 2 | `ingest.js:7`, `analyze.js:96` | Complete the list and probe all of them; take UA names from each vendor's official docs |
| 9 | **Factual error** | The fixture server's regex includes `Google-Extended`, but that is only a robots.txt token, **not an HTTP UA** | `server/index.js:35` | Remove it; a knowledgeable judge would catch it immediately |
| 10 | **SSRF guard can be bypassed** | `127.0.0.2`, `localhost.`, `[::ffff:127.0.0.1]`, and `0.0.0.0` all passed the check (tested). Also, from reading the code, redirects and browser subresource requests are not checked | `server/index.js:17` onward; `ingest.js:16` | **Don't claim "SSRF protection" in the demo.** Either restrict analysis to the test pages plus an allowlist, or validate IPs after DNS resolution and check every redirect hop |
| 11 | **The test set is circular** | The 7 test pages and the detector were written by the same AI in the same 30 minutes, so "all pass" proves almost nothing | `server/fixtures/` | Re-evaluate with the real-case replica set and the external attack library (section 5) |

## 4. The refined idea

**One-liner (usable as-is)**

> Attackers have started writing to AI agents inside ordinary web pages. InjectionLens shows exactly what each kind of agent would ingest from a page — including what humans can't see — and which of those instructions could reach real damage.

**Shift the problem statement from "could happen" to "already happening"**: in 2026, Unit 42, Google, Forcepoint, and academic researchers all found AI-directed instructions on real web pages, and the malicious category grew 32% (relative) in three months.

**Change the core criteria to**: is this text talking to an AI, what is its intent, and can the target agent carry it out? Being hidden is only a boosting signal, not a gate (37.8% of real payloads are visible plaintext).

**Target users (pick one and go deep)**: teams that let AI read untrusted pages on their behalf and **make decisions based on them**, such as Trust & Safety teams using AI to review ads or content, recruiters using AI to screen résumés, and developers of browser agents.

**Suggested new capability templates**:
- `decision agent` (ad review or résumé screening): no tools, but **the output itself is the capability**. "Approve the scam ad" or "rank this person first" is the actual harm. None of the three existing templates covers this.
- `coding agent (shell)`: corresponds to the `rm -rf` payloads Forcepoint found.

**Demo storyline**: Replicate Unit 42's scam-ad landing page. To a human it looks like a normal ad, but the page leaves several "please approve" instructions for the AI reviewer, spread across a visible footer, data-* attributes, CSS-hidden elements, comments, and JSON-LD. Show which pipeline reads which instruction, and how the impact level changes after switching to `decision agent`. This story covers both the "AI-powered cybersecurity" and "phishing and scam detection" areas listed by the hackathon, and echoes the folder name ScamLens: *Scammers now write to your AI.*

**How to state the differentiation**: hidden-text scanning is already commoditized (there's an off-the-shelf Chrome extension); guardrail APIs only give a verdict, without telling you which pipeline or which node; IPI-Proxy is a tool for attacking agents, and we use its attack library for evaluation; web-scale research is telemetry, not a tool a team can point at a page.

**State the limitations up front**: the UA probe is only a lower bound and can't catch cloaking based on behavioral fingerprints; screenshot and OCR-based agents aren't covered; no scanner can "solve" prompt injection. What InjectionLens does is reduce the risk and make it visible.

## 7. Likely judge questions

- **"Isn't this just a regex scanner?"** Regex is only the cheapest first layer. The value is in comparing sources across pipelines, pinpointing nodes, analyzing capability reachability, and evaluating on real data. If pressed, walk through the limitations directly.
- **"How is this different from Lakera or Model Armor?"** They return a verdict on the text you give them. We answer which kind of agent would read what, at which spot on the page, and what it could do after reading it.
- **"You built this in 30 minutes?"** Yes. The skeleton was AI-generated, and that's disclosed. The real work is the audit, the fixes, and the evaluation, which the commit history shows.
- **"What about false positives?"** Answer with the false-positive rate measured on real pages in section 5.
- **"Can attackers bypass it?"** Yes. The video itself shows our own bypass and fix. That's why we advocate defense in depth rather than treating InjectionLens as a silver bullet.
